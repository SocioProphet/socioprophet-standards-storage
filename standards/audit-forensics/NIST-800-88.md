## Overview

This document specifies the forensic-ready audit trail requirements for the SocioProphet
platform, aligned with NIST SP 800-88 Rev. 1 (Guidelines for Media Sanitization) and
NIST SP 800-53 Rev. 5 AU-family controls.

The goal is an audit trail that is: **immutable**, **cryptographically verifiable**,
**non-repudiable**, **complete**, and **admissible** as legal/regulatory evidence.

This document uses RFC 2119 language: **MUST**, **SHOULD**, **MAY**.

## Immutable Audit Trail Requirements

### Write-Once-Read-Many (WORM) Storage

Audit log storage **MUST** be configured as WORM:

- Write operations: append-only new records; no overwrite or delete.
- Read operations: unrestricted for authorized audit roles.
- Administrative deletion: prohibited by technical control, not just policy.
- Retention period: minimum 3 years; longer if regulatory requirements demand it.

Acceptable WORM implementations:
- Object-lock-enabled cloud object storage (e.g., S3 Object Lock compliance mode).
- Hardware WORM drives with firmware-enforced write protection.
- Append-only database tables with DDL permission removed from all runtime roles.

### Append-Only Constraint

The audit trail **MUST** enforce append-only at every layer:

| Layer | Enforcement |
|-------|------------|
| Application | Audit library exposes only `emit(event)`, no delete/update API |
| Storage runtime | Runtime credentials scoped to `PUT` only; no `DELETE` or `PATCH` |
| Infrastructure | WORM bucket policy or hardware lock |
| Key management | Encryption keys for audit storage non-exportable from HSM |

### Cryptographic Hash Chain

Each audit record **MUST** include the SHA-256 hash of the immediately preceding record,
forming a tamper-evident chain.

```
Record N-1
  SHA-256(Record N-1) ─────────────────────────────┐
                                                    │
Record N                                            │
  {                                                 │
    "event_id": "...",                              │
    "prev_hash": "<SHA-256 of Record N-1>",  ◄──────┘
    "payload": { ... },
    "signature": "<ECDSA P-256 over entire record>"
  }
```

Verification procedure:
1. Compute SHA-256 of every record.
2. Confirm `record[N].prev_hash == SHA-256(record[N-1])` for all N.
3. Verify ECDSA P-256 signature of every record against the audit signing key.
4. Confirm RFC 3161 TSA tokens parse and chain to the TSA root certificate.

Any break in the hash chain or invalid signature is an `AuditIntegrityViolation` event
and **MUST** trigger a P0 security incident.

### Digital Signatures on Every Entry

Every audit record **MUST** be signed individually:

- Algorithm: ECDSA P-256
- Signing key: dedicated audit signing key, stored in FIPS 140-2 Level 2+ HSM
- Scope: signature covers the complete serialized record (all fields, including `prev_hash`)
- Key rotation: every 12 months; previous key archived and used for historical verification

Audit signing keys **MUST NOT** be used for any other purpose.

### RFC 3161 Trusted Timestamp Authority Integration

Every audit record **MUST** include an RFC 3161 TSA token:

1. Compute SHA-256 of the record payload (pre-signature).
2. Submit hash to RFC 3161-compliant TSA.
3. Receive signed `TimeStampToken`; embed in the record.
4. Sign the full record (including the TSA token) with the audit signing key.

This prevents both backdating and forward-dating of audit records.

Acceptable TSA providers: any provider operating under RFC 3161 with FIPS-approved algorithms
(SHA-256 minimum). TSA root certificate **MUST** be pinned and periodically verified.

## Chain-of-Custody Procedures

### Audit Trail Preservation

When an audit trail export is required for legal, regulatory, or investigative purposes:

1. **Authorize** — Audit export **MUST** be approved by two authorized audit principals
   (four-eyes principle).
2. **Export** — Generate a signed, timestamped export package:
   - All records in the requested time window (NDJSON format)
   - Verification manifest (record count, first/last hash, export timestamp, exporter identity)
   - ECDSA P-256 signature over the entire export package
   - RFC 3161 TSA token for the export
3. **Log** — Emit `AuditTrailExported` event (this event is itself immutable in the audit log).
4. **Transfer** — Deliver export via encrypted channel (TLS 1.3) to authorized recipient.
5. **Verify** — Recipient verifies package signature and hash chain before use.

### Evidence Handling

- Audit evidence **MUST** be handled under documented chain-of-custody.
- Every transfer of evidence **MUST** be recorded (who, what, when, from/to).
- Evidence copies **MUST** be verified against original hash at each transfer.
- Evidence **MUST NOT** be modified; any annotation added in a separate metadata layer.

### Forensic Readiness

The system **MUST** maintain forensic readiness at all times:

| Capability | Requirement |
|-----------|-------------|
| Time to export audit trail | < 4 hours for any 90-day window |
| Hash chain verification | Automated; < 30 minutes for 1 year of records |
| Record correlation | Cross-reference by `session_id`, `principal_id`, `build_id` |
| Timezone normalization | All timestamps in UTC; offset recorded where source differs |
| Long-term storage integrity | Periodic (weekly) automated hash chain verification |

### Post-Incident Investigation Procedures

1. **Scope** — Identify the time window and principals involved.
2. **Extract** — Export audit records for the relevant window using the chain-of-custody procedure.
3. **Verify** — Replay hash chain; verify all signatures; confirm TSA tokens.
4. **Reconstruct** — Build event timeline sorted by `timestamp`, grouped by `session_id`.
5. **Attribute** — Map each action to a principal using `principal_id` and authentication records.
6. **Preserve** — Archive investigation package in WORM storage with its own hash and signature.
7. **Report** — Produce incident report referencing specific `event_id` values as evidence.
8. **Remediate** — Address root cause; update controls; re-test.

## Non-Repudiation Requirements

### Digital Signature Binding

Every audit record **MUST** include:
- ECDSA P-256 signature covering all fields (prevents record tampering)
- Signature key ID (enables key rotation without losing verifiability)
- `principal_id` tied to the OIDC subject claim of the acting identity

This means the principal cannot deny having performed an action because:
1. Their OIDC token (which they authenticated for) is recorded.
2. The record is signed by a key they cannot revoke (audit signing key in HSM).
3. An independent RFC 3161 TSA token records the wall-clock time.

### Timestamp Authority Tokens

RFC 3161 TSA tokens provide legally-recognized proof of time for each record:
- Issued by an independent third-party TSA.
- Cover the SHA-256 hash of the record payload.
- TSA certificate chain verified and pinned.
- Tokens archived alongside records; never discarded.

### Key Binding to Principal Identity

Each authentication event links:
- The cryptographic key used (signing key ID)
- The principal's OIDC `sub` claim
- The MFA method and device used (where applicable)

This three-way binding (identity + key + MFA) provides strong non-repudiation for
high-value operations.

## Compliance with NIST SP 800-88 Guidelines

NIST SP 800-88 Rev. 1 focuses on media sanitization; its principles of data lifecycle
management and evidence preservation apply directly to audit trail management:

| NIST SP 800-88 Principle | Implementation |
|-------------------------|----------------|
| Data categorization | Audit logs classified as HIGH sensitivity; handled accordingly |
| Sanitization before disposal | Audit storage decommissioned only after cryptographic key destruction and regulatory retention period |
| Verification of sanitization | Destruction verified and recorded in a final audit entry (signed by HSM before key destruction) |
| Documentation | Chain-of-custody records maintained per this document |
| Incident response | Procedures defined in §Post-Incident Investigation Procedures |

## Audit Storage Architecture

```
┌─────────────────────────────────────────────────────────────────┐
│  Platform Components                                            │
│  (workspace controller, build executor, policy engine, etc.)    │
└────────────────────────┬────────────────────────────────────────┘
                         │ emit(event) — append only
                         ▼
┌─────────────────────────────────────────────────────────────────┐
│  Audit Emitter Library                                          │
│  - Fetch TSA token for event hash                               │
│  - Append prev_hash from last record                            │
│  - Sign record with audit ECDSA P-256 key (via HSM)             │
│  - Serialize to NDJSON                                          │
└────────────────────────┬────────────────────────────────────────┘
                         │ TLS 1.3 + mTLS
                         ▼
┌─────────────────────────────────────────────────────────────────┐
│  WORM Audit Storage                                             │
│  - Object lock (compliance mode, 3-year retention)              │
│  - AES-256-GCM encryption at rest                               │
│  - HMAC-SHA-256 integrity seals per storage segment             │
│  - No DELETE or PATCH permissions on any runtime role           │
└────────────────────────┬────────────────────────────────────────┘
                         │ scheduled verification job
                         ▼
┌─────────────────────────────────────────────────────────────────┐
│  Integrity Verifier (weekly)                                    │
│  - Replay full hash chain                                        │
│  - Verify all signatures                                         │
│  - Verify TSA token chains                                       │
│  - Emit AuditIntegrityVerified event (or raise P0 alert)         │
└─────────────────────────────────────────────────────────────────┘
```
