## Overview

The SocioProphet platform's audit trail is a foundational component of its security and compliance posture. It provides the evidence base for all NIST 800-53 control assertions, the forensic record for incident investigations, and the non-repudiation chain for all consequential operations.

An audit trail is only as trustworthy as its integrity guarantees. This document specifies the technical and procedural requirements that ensure audit records cannot be altered, deleted, or fabricated — either by an attacker or by an insider — without detection.

The requirements in this document apply to:

- All services that emit audit events to the platform audit pipeline
- The audit pipeline infrastructure (ingest, store, verify)
- Security operations personnel who access audit records
- Forensic investigators who collect and analyze audit evidence

### Design Invariants

1. **Append-only:** No audit record may ever be modified or deleted before its retention expiry.
2. **Tamper-evident:** Any modification to the audit store is detectable via hash chain verification.
3. **Non-repudiable:** Every audit batch is signed by a service identity that cannot plausibly deny having created it.
4. **Authoritative time:** Every audit record carries an authoritative timestamp from an RFC 3161 timestamp authority (TSA).
5. **Cryptographically complete:** The record's integrity can be fully verified using only the record content, the hash chain, the batch signature, and the TSA certificate chain.

## Write-Once-Read-Many Storage Requirements

### Storage Technology

Audit records are stored in MinIO configured with S3 Object Locking in Compliance mode. Object Locking in Compliance mode means:

- No principal, including the storage administrator, can delete or overwrite a locked object before its retention period expires.
- The retention mode and retention date cannot be shortened once set; they can only be extended.
- There is no legal hold bypass or administrative override within the platform.

> This is distinct from Governance mode, which allows administrators to override. Compliance mode is mandatory for audit storage.

### Storage Configuration Requirements

```yaml
# MinIO bucket configuration for audit storage
bucket_name: socioprophet-audit
versioning: enabled          # Required; supports object locking
object_locking: enabled
locking_mode: COMPLIANCE     # Not GOVERNANCE
default_retention:
  mode: COMPLIANCE
  days: 2557               # 7 years (365 * 7 + 2 for leap years)
encryption:
  algorithm: AES-256-GCM   # SSE with AES-256-GCM
  key_source: vault         # Key managed by HashiCorp Vault
  key_rotation: 90d
replication:
  enabled: true
  destinations:
    - region: secondary
      mode: async
      also_compliance: true # Replication target also has COMPLIANCE locking
```

### Hot / Warm / Cold Tiering

| Tier | Duration | Storage Class | Access Pattern |
|---|---|---|---|
| Hot | 0–90 days | Standard | Active investigations, real-time monitoring, recent audit queries |
| Warm | 91 days – 2 years | Infrequent Access | Periodic review, quarterly assessments, audit queries |
| Cold (compliance archive) | 2 years – 7 years | Archive (Glacier-equivalent) | Annual review, regulatory requests, litigation hold |

Tiering is managed by MinIO lifecycle policies. Lifecycle policies operate only on the storage class (cost) and do not affect Object Locking retention — locked objects remain locked regardless of storage tier.

### Replication and Durability

The audit store is replicated to a geographically separated secondary store. Replication is synchronous for the hot tier (ensuring that a record is in both locations before the write is acknowledged to the audit pipeline). Warm and cold tiers use asynchronous replication with a maximum replication lag of 4 hours.

Durability target: 99.999999999% (11 nines). This is achieved through erasure coding within each store and replication across stores.

## Cryptographic Hash Chains

### Purpose

A hash chain ensures that the complete set of audit records is tamper-evident. An attacker who modifies, deletes, or inserts a record anywhere in the chain causes all subsequent hash links to become invalid. The chain is verified by recomputing every hash in sequence and comparing to the stored values.

### Hash Chain Construction

Each audit event record includes a `prev_hash` field containing the SHA-256 hash of the previous record in the same stream. The first record in a stream has `prev_hash` set to the SHA-256 of the stream's genesis block (the WORM-stored stream metadata).

```
Genesis Block
    │
    │  SHA-256(genesis_block)
    ▼
Record 1  ← contains: event_payload, prev_hash = H(genesis)
    │
    │  SHA-256(record_1_canonical_bytes)
    ▼
Record 2  ← contains: event_payload, prev_hash = H(record_1)
    │
    │  SHA-256(record_2_canonical_bytes)
    ▼
Record 3  ← contains: event_payload, prev_hash = H(record_2)
    │
   ...
```

**Canonical bytes:** The hash input is the canonical JSON encoding of the record with all fields in lexicographic key order, with no trailing whitespace, using UTF-8 encoding. This definition is normative and must be used consistently to enable independent verification.

### Hash Algorithm

SHA-256 (FIPS 180-4). SHA-384 may be substituted for high-assurance streams (key management audit trail). SHA-1 and MD5 are prohibited.

### Multi-Stream Hash Chains

The audit pipeline maintains separate hash chains per audit stream. Streams are defined by:

- `source_service` — the service that emitted the event
- `event_family` — the category of events (AUTH, AUTHZ, CRYPTO, SYSTEM, DATA)

Each stream has an independent chain rooted in its genesis block. Cross-stream correlation is performed at analysis time using timestamps and correlation IDs, not by merging chains.

### Batch Sealing

Every 60 seconds (configurable), the audit pipeline seals the current batch of records in each stream. Sealing involves:

1. Computing the SHA-256 of the last record in the batch.
2. Requesting an RFC 3161 timestamp for the SHA-256 value.
3. Creating a signed batch envelope (see Digital Signatures section).
4. Writing the batch envelope and all records in the batch to the WORM store in a single atomic operation.

A batch with fewer than one record is sealed on a timer to ensure that the absence of events is also auditable (the sealed empty batch proves no events were suppressed).

## Digital Signatures for Non-Repudiation

### Signature Algorithm

ECDSA-P256 (FIPS 186-5). The signing key is held in the HSM-backed signing service and is accessible only to the audit pipeline's signing component. The signing certificate chain is rooted in the platform CA.

### What Is Signed

Each batch envelope is signed. The signature input is the canonical JSON of the batch envelope, which includes:

```json
{
  "stream_id": "...",
  "batch_seq": 42,
  "batch_start_time": "2026-01-27T12:00:00.000Z",
  "batch_end_time": "2026-01-27T12:01:00.000Z",
  "record_count": 17,
  "first_record_hash": "sha256:abc...",
  "last_record_hash": "sha256:def...",
  "chain_root": "sha256:genesis...",
  "rfc3161_timestamp": { ... },
  "signer_certificate": "...",
  "signer_spiffe_id": "spiffe://socioprophet.org/ns/audit/sa/audit-pipeline"
}
```

The signature is stored in the `signature` field of the batch envelope and is also stored separately as a detached signature object in the WORM bucket.

### Signature Verification

Any party with access to the audit bucket and the platform CA certificate chain can independently verify the signature:

1. Retrieve the batch envelope and the detached signature.
2. Verify the signer certificate chain up to the platform root CA.
3. Verify that the certificate's SPIFFE SAN matches `spiffe://socioprophet.org/ns/audit/sa/audit-pipeline`.
4. Verify the ECDSA-P256 signature over the canonical batch envelope JSON.
5. Verify the RFC 3161 timestamp (see next section).

## RFC 3161 Timestamps

### Purpose

RFC 3161 timestamps provide authoritative, third-party-verifiable proof of when an audit batch was sealed. They prevent backdating of audit records (inserting a record with a falsified past timestamp and claiming it was always there).

### Timestamp Request Process

When a batch is sealed:

1. The audit pipeline computes the SHA-256 of the canonical batch envelope.
2. The pipeline submits a timestamp request (TSQ) per RFC 3161 to the configured Timestamp Authority (TSA).
3. The TSA returns a timestamp response (TSR) containing: the hash algorithm, the hash value, the time (UTC), and the TSA's signature over these fields.
4. The TSR is embedded in the batch envelope before the batch is signed.

### Timestamp Authority Requirements

The TSA used by the SocioProphet platform must:

- Be operated by a trusted authority independent of SocioProphet (no self-signing).
- Use SHA-256 for message imprint hashing.
- Issue TSRs with UTC time accurate to within 1 second.
- Maintain an OCSP responder for its own certificate.
- Provide TSR retention for at least 10 years.

The configured TSA and its certificate chain are stored in `sociosphere/iac/audit/tsa-config.yaml`.

### Timestamp Verification

Timestamp verification is part of the standard batch integrity verification procedure (see Audit Log Integrity Verification section). A batch whose RFC 3161 timestamp cannot be verified against the TSA's certificate chain is considered integrity-compromised.

## Retention Policy

### Retention Tiers

| Data Category | Hot Retention | Total Retention | Authority |
|---|---|---|---|
| Security audit logs (authentication, authorization, crypto ops) | 90 days | 7 years | Compliance requirement |
| Operational logs (non-security) | 90 days | 1 year | Platform policy |
| Cryptographic key records | Lifetime of key | Lifetime + 7 years | NIST SP 800-57 |
| Incident response evidence | Duration of investigation | 7 years post-closure | Compliance requirement |
| SBOM and artifact signatures | Lifetime of artifact | Lifetime + 7 years | SLSA requirements |
| Access logs (data access) | 90 days | 7 years | Compliance requirement |
| Configuration change logs | 90 days | 7 years | Compliance requirement |

### Retention Enforcement

Retention is enforced through MinIO Object Locking (Compliance mode). The retention date is set at ingest and cannot be shortened. The retention period is calculated as: `ingest_date + retention_days`.

A secondary enforcement mechanism is the retention monitor, which runs daily and verifies that all WORM objects have retention locks set correctly. Any object found without a valid retention lock is a critical finding and triggers an immediate alert.

### Legal Hold

A legal hold extends the retention of specified records beyond their normal retention period, indefinitely, until the hold is released. Legal holds are set and released only by the legal team and require written authorization. Legal hold events are themselves audited.

### End-of-Retention Deletion

When a record's retention period expires:

1. If no legal hold is active, the record transitions to pending deletion.
2. The deletion is logged to the audit trail (the deletion event itself has a 7-year retention).
3. For encrypted data: the record's data encryption key (DEK) is destroyed in Vault (cryptographic erasure). The ciphertext remains but is permanently unreadable.
4. For physical media: NIST 800-88 Rev 1 sanitization procedures apply (see Media Sanitization section).

## Chain-of-Custody Procedures

### Definition

Chain of custody is the documented, unbroken sequence of possession and handling of audit evidence from its creation to its presentation in an investigation, hearing, or regulatory review. A broken chain of custody may render evidence inadmissible.

### Collection Procedures

When audit records are collected for an investigation or regulatory request:

1. The requesting investigator or legal contact submits a formal evidence request through the incident tracking system. The request is audited.
2. The platform security team identifies the relevant audit streams, time ranges, and record identifiers.
3. An evidence export is performed by an authorized evidence custodian (a designated role, not the general security operations team).
4. The exported evidence package includes: all relevant records, the hash chain for each stream, all batch envelopes with signatures, all RFC 3161 timestamps, and the platform CA certificate chain.
5. The SHA-256 of the entire evidence package is computed and recorded in the incident tracking system.
6. The evidence package is transferred via encrypted channel (AES-256-GCM, TLS 1.3) to the requesting party. The transfer is audited.
7. The receiving party confirms receipt and records the SHA-256 they received. The platform compares this to the SHA-256 recorded in step 5. Any mismatch is a critical integrity failure.

### Custodian Record

Each evidence package is tracked with a custodian log:

| Field | Description |
|---|---|
| Request ID | Unique incident or regulatory request identifier |
| Requestor | Identity of the party requesting evidence |
| Custodian | Identity of the evidence custodian who performed the export |
| Export time | UTC timestamp of export |
| Records included | Count and hash of included records |
| Package hash | SHA-256 of the complete evidence package |
| Transfer method | How the package was transferred |
| Recipient confirmation | Receipt confirmation and SHA-256 match verification |

### Preservation Order

If a preservation order (legal hold) is received, the platform security team, in coordination with legal counsel:

1. Identifies all relevant records and streams within 24 hours.
2. Sets a legal hold on all affected objects in the WORM store.
3. Documents the legal hold in the incident tracking system with the legal order reference.
4. Does not delete, modify, or allow expiry of any held records until the hold is released by legal counsel.

## Non-Repudiation Requirements

Non-repudiation means that a party who performed an action cannot credibly deny having done so. The audit trail provides non-repudiation through the combination of:

1. **Identity binding:** Every event contains the SPIFFE SVID or OIDC subject of the acting party. These identities are issued by the platform's trusted identity infrastructure and are not self-asserted.
2. **Digital signature:** Every audit batch is signed with the audit pipeline's ECDSA-P256 key. This proves the batch was sealed by the authorized pipeline, not fabricated later.
3. **RFC 3161 timestamp:** The TSA's signature proves the batch existed at the stated time, preventing backdating.
4. **Hash chain:** The hash chain proves no records were inserted, deleted, or modified after sealing.
5. **WORM storage:** Object Locking in Compliance mode provides physical non-repudiation — the record cannot have been deleted from the store.

### Non-Repudiation Coverage Matrix

| Scenario | How Non-Repudiation Is Maintained |
|---|---|
| User claims they never logged in | AUTH_SUCCESS event with OIDC jti; TSA timestamp; WORM storage |
| Service claims it never accessed data | DATA_READ event with SPIFFE SVID; WORM storage |
| Operator claims they never changed policy | SYSTEM_POLICY_CHANGED with OIDC subject; hash of change; WORM |
| Attacker inserts a false log entry | Hash chain break detected at next verification |
| Attacker deletes a log entry | Hash chain gap detected; WORM prevents physical deletion |
| Insider alters a log entry in place | Hash chain break; WORM prevents in-place writes |
| Timestamp is backdated | RFC 3161 TSA timestamp proves actual sealing time |

## Media Sanitization Compliance

### NIST 800-88 Sanitization Categories

NIST SP 800-88 Rev 1 defines three sanitization categories:

| Category | Method | When to Use |
|---|---|---|
| Clear | Overwrite with known data pattern | Low-sensitivity media being reused within the organization |
| Purge | Cryptographic erase or verified overwrite | Medium-to-high sensitivity media being reused or repurposed |
| Destroy | Physical destruction (shred, disintegrate, incinerate) | High-sensitivity media being retired or decommissioned |

### SocioProphet Sanitization Policy

| Scenario | Required Method | Procedure |
|---|---|---|
| Cloud storage (object store) end-of-retention | Cryptographic erase (Purge) | Destroy DEK in Vault; ciphertext retained but permanently unreadable |
| Cloud storage hard media (data center decommission) | Destroy | Third-party certified media destruction; certificate of destruction retained 7 years |
| Developer workstation (AES-256 encrypted) | Cryptographic erase | DEK destruction; drive retention per organization policy |
| HSM end-of-life | Vendor Destroy (Zeroize) | HSM zeroization per vendor procedure; documented and audited |
| Backup media (tape, removable) | Purge or Destroy | Minimum: cryptographic erase; preferred: physical destruction |

### Cryptographic Erase Procedure

Cryptographic erase is applicable when all data on the media is encrypted with a key that can be destroyed. The SocioProphet platform uses AES-256-GCM for all data at rest, with per-resource or per-bucket DEKs managed by HashiCorp Vault.

Erase procedure:

1. Confirm that all data to be erased is encrypted with the identified DEK.
2. Issue a key destruction command to Vault for the DEK. Vault removes all key material and records the destruction event.
3. Verify that the key is no longer accessible by attempting to use it (expect failure).
4. Record the destruction in the audit trail (KEY_DESTROYED event).
5. Document the erasure in the media sanitization log with: date, media identifier, key identifier, method, and verifier identity.

## Audit Log Integrity Verification

### Automated Continuous Verification

The audit integrity monitor runs continuously and performs:

- **Real-time hash chain validation:** As each record arrives at the ingest pipeline, its `prev_hash` is validated against the hash of the previous record.
- **Batch seal verification:** After each batch is sealed, the signature and RFC 3161 timestamp are verified before the batch is committed to WORM storage.
- **Replication consistency check:** Hourly comparison of record counts and last-record hashes between primary and secondary stores.

Any failure in automated verification is a critical alert (immediate page to security on-call).

### Periodic Full Verification

A full integrity verification runs weekly (for the hot tier) and quarterly (for the warm tier). Full verification:

1. Retrieves every record in the stream from the WORM store.
2. Recomputes the SHA-256 of each record's canonical bytes.
3. Verifies the `prev_hash` chain from genesis block through the latest record.
4. Verifies each batch envelope signature (ECDSA-P256).
5. Verifies each RFC 3161 timestamp against the TSA's certificate chain (checking OCSP for the TSA certificate status).
6. Reports the result, including the genesis block hash, the latest record hash, and the total record count.

The full verification report is itself signed and stored in the WORM audit store.

### Manual Verification Procedure

For forensic investigations or regulatory requests, a manual full verification can be triggered by the security operations team. The procedure is identical to the automated full verification but is performed on a scoped set of records (by stream, time range, or record IDs) rather than the entire archive.

Manual verification outputs a verification certificate:

```
Verification Certificate
========================
Verified by: [identity]
Verification time (RFC 3161 sealed): [timestamp]
Stream: [stream_id]
Record range: [first_seq] – [last_seq]
Record count: [count]
Genesis hash: sha256:[genesis_hash]
Terminal hash: sha256:[terminal_hash]
All hashes valid: YES / NO [if NO: list of broken links]
All signatures valid: YES / NO [if NO: list of failed signatures]
All timestamps valid: YES / NO [if NO: list of failed timestamps]
Certificate signature: [ECDSA-P256 signature by verifier]
```

## Evidence Preservation for Forensic Investigations

### Pre-Forensics Snapshot

When an incident is declared, the following forensic evidence preservation steps are taken immediately (before any investigation activity):

1. **Freeze affected streams:** Mark the relevant audit streams with the incident ID. Any records added after the freeze are tagged with the incident ID for traceability.
2. **Snapshot current state:** Record the current terminal hash of each relevant stream. This establishes the state of the evidence at the time the incident was declared.
3. **Legal hold:** Apply a legal hold to all affected WORM objects. This prevents any scheduled expiry from occurring during the investigation.

### Forensic Evidence Package

A complete forensic evidence package for an incident contains:

| Component | Description | Format |
|---|---|---|
| Audit records | All events in scope, canonical JSON | WORM export |
| Hash chain proof | Chain verification from genesis to terminal | Verification certificate |
| Batch envelopes | Signed batch envelopes covering the scope | JSON + detached signature |
| RFC 3161 timestamps | TSRs for all batches in scope | DER-encoded TSR |
| Platform CA chain | Platform root CA and intermediate certificates | PEM bundle |
| TSA certificate chain | Timestamp authority certificate chain | PEM bundle |
| Identity records | SVID or OIDC token metadata for subjects involved | JSON |
| Network flow logs | Captured flows for affected workloads | PCAP or structured log |
| WORM object metadata | Object Lock status, retention dates for all objects | MinIO metadata export |
| Custody log | Complete chain-of-custody log | Signed PDF |

### Evidence Integrity at Handoff

When the evidence package is handed to an external investigator or regulatory body:

1. The SHA-256 of the complete package (as a tar archive) is recorded in the custody log.
2. The package is encrypted with the recipient's public key (ECDSA-P256/ECDH key exchange) for transit.
3. The recipient decrypts and independently verifies the SHA-256 of the received package.
4. The recipient executes the hash chain and signature verification procedures using the included CA and TSA certificate chains.
5. The recipient signs a receipt acknowledgment with their own certificate, confirming the SHA-256 they received and that verification passed.
